# Note-writing build and evaluation plan — one-module pilot first

Status: historical design for an Accounting/DOCX pilot. It predates the current implementation and is not the active output-format decision. The user has selected LaTeX for Econometrics 1, Machine Learning, Microeconomics 2, and Corporate Finance and Capital Markets; see [the active LaTeX workflow](latex-note-workflow.md). The old Accounting/DOCX sections below are retained as evaluation history, not commands to generate DOCX notes. Raw/gold material and detailed scoring records belong in a private data root outside this project.

## 1. Start by defining a fair one-module evaluation

Choose **Accounting, Year 1 Term 2**, as the first pilot, not because every future note will be Word, but because the folder has a relatively rich pairing of lecture handouts/slides, MCQ questions and answers, tutorial slides, spreadsheet worked answers, a mock question/answer pair, and a large user-authored DOCX. Begin with one lecture/tutorial pair and scale to all ten only if the evaluation works. Coding and math renderers are later milestones using their own gold notes.

**Freeze the split before writing prompts or notes:**

- Style references: a *content-stripped* profile derived from other Word notes (Microeconomics/Macroeconomics), plus blank style definitions/layout from Accounting. If necessary, use disjoint Accounting lecture sections only after checking they do not contain test-topic prose. Never put the full Accounting gold document into the generator's retrieval index or model context. A template copied with the gold body still inside it is leakage.
- Development slice: Accounting Lecture 2 + Tutorial 2, with only their relevant source files. Use this to iterate extraction, rendering and prompts against a disclosed gold slice.
- Locked test slice: Accounting Lecture 1 + Tutorial 1. Available sources include `01a ... Handout EFDS 2026.pdf/.pptx`, `01b ... Lecture EFDS.pptx`, question-only `01c`/`01e` MCQs, answer-bearing `01d`/`01f` MCQs, `01g CVP Healthcare Question.pdf`, and `Tutorial Slides/Tutorial slides - week 1.pdf`. Extract the matching gold section from `Accounting Notes.docx` into a private, evaluator-only file. Never show this gold text to the generator, prompt tuner or retrieved-source search. Keep an additional held-out, more numerical slice (e.g. Lecture/Tutorial 5) for a later robustness check rather than optimizing solely for Lecture 1.
- Rights and academic-integrity gate: do not upload licensed books or institutional slides to an external provider without authorization. Exclude graded submissions, personal journals and other people's private work. DSA's syllabus explicitly forbids AI-written code for individual homework unless allowed; later coding evaluations must use lecture/practice material only, not produce assessed solutions.

A single gold note is not a truth oracle. The Accounting DOCX includes equations, figures and some blank-looking quantities in text extraction, while its OOXML has a TOC, 20 Heading 1 paragraphs, 33 Heading 2 paragraphs, six tables and 267 embedded drawings/media parts. The generator/evaluator must inspect the formatted page, not just extracted text. A user note can omit content, include a typo or rely on a video, EdStem answer, textbook or InSendi page missing from OneDrive. Mark such cases **gold-only / source missing / gold error / deliberate paraphrase**, not automatically a model failure or a fact to copy.

### Build the reference set, not merely a text similarity score

Before generating anything, a human-reviewed evaluator constructs a small **atomic coverage ledger** from the official source slice: one entry per definition, assumption, formula and units, worked step, important caveat, figure/table, and tutorial insight. Each entry has a source ID + exact page/slide, importance (`essential`, `supporting`, `optional`), intended note location, whether the gold expresses it, and whether it is actually accessible. A formula hidden as an image is reviewed from the rendered page. The gold section is segmented into the same kinds of units separately, with links to sources where possible.

Compare a produced note on independent axes:

1. **Faithfulness:** every substantive statement is backed by an exact source locator; flag unsupported claims, contradictions and wrong units/equations. Numeric examples are independently recomputed where feasible.
2. **Source coverage:** essential/supporting evidence units represented accurately, including tables/figures and answer-method insights. Report the denominator and all deliberately omitted, uncertain or unavailable items. No credit for merely being long.
3. **Gold alignment:** concept/solution overlap with the held-out user's note, including what the user selected to include, but do not penalize correct additions from official sources or reward copied mistakes. Measure paraphrase/structure rather than string overlap as the principal score.
4. **Personal style:** user-reviewed heading/TOC hierarchy, bullet nesting, concise definition-plus-consequence phrasing, use of examples and worked solutions, visual density, and faithful image/table treatment. A shorter *sentence-level tone* must not turn into a shorter *information set*. Do a blinded pairwise review of baseline vs style-aware candidate, with source coverage shown separately.
5. **Artifact quality and effort:** open/inspect DOCX (styles, equations, figures, page breaks, TOC), render to PDF when a renderer is available and review representative pages, measure manual edit time, tokens/cost, and incremental-rebuild stability.

Initial non-negotiable gate: no critical factual/numerical error, all user-designated essential units present or explicitly marked missing, and a readable/openable artifact. Set numerical secondary coverage/style thresholds only after annotating the pilot ledger and seeing baseline scores; do not invent a success threshold that a human gold note itself fails. Use a second reviewer or a user spot-check on contested units. LLM-as-judge can triage but cannot be the sole grader.

Compare two reproducible systems on identical, frozen inputs: (A) a simple baseline that drafts from only the selected official materials, and (B) the staged style-aware system. Record model/version, prompts, hashes, included sources, extraction versions, decisions, outputs, scoring rubric, latency and cost. Run the locked test once after choosing the system on development data; later changes need a newly frozen test slice. Full gold never enters the candidate's prompt, search index or few-shot set.

## 2. Build the source and provenance layer

Create a local Python CLI first; defer web UI, agents and vector infrastructure. Command boundaries: `inventory`, `inspect`, `freeze`, `extract`, `coverage`, `draft`, `render`, `evaluate`. Start with a manifest that selects exact source IDs from the OneDrive GVfs mount; copy only authorized selected files to a private, read-only snapshot or verify their hashes at read time. Keep edition, academic year, lecturer/student origin, role (`lecture`, `tutorial_question`, `tutorial_solution`, `textbook`, `student_style_gold`, etc.), rights, and modified/hash identity. Do not ingest `.Rproj.user`, `.git`, notebook checkpoints, temporary files or private assessments by default. If a source fails, record the gap and do not pretend a module is complete.

Normalize extraction into anchored evidence blocks: `source_id`, `version`, `locator` (page, slide, cell, reply or timestamp), `text`, `asset_refs`, `extraction_method`, `quality_flag`, `authority`, and `topic`. Use SQLite FTS as a transparent retrieval baseline; derive semantic indexes only after measuring missed facts. PDF parsing is per page with diagram/OCR review for bad pages. PPTX includes notes and embedded pictures, DOCX includes headings/images/OMML math, XLSX includes formulas and units, Rmd/IPYNB includes text and code, and textbooks are chapter-scoped with rights controls. Do not accept model-inferred formulas when the PDF text layer dropped a symbol.

Reserve separate adapters for Panopto (download entitlement, captions, time-aligned selected frames and slides), EdStem/Ed (thread/reply roles, accepted/staff answers, attachments and chronology), and InSendi/Hub/online readings. The user's separate access is not yet a verified export path. Use only approved access methods; no guessed APIs, public YouTube re-upload or bulk cloud processing by default. Report exactly what course/lecture and source-type coverage remains absent.

## 3. Separate coverage planning, writing style and rendering

A structured intermediate note model should hold `Section`, `EvidenceUnit`, and blocks such as `bullet`, `definition`, `equation`, `proof`, `worked_example`, `exercise_question`, `answer_method`, `code`, `table`, `figure`. Each block keeps source references, gold alignment only in evaluation records, and review status. Planning asks *what must be covered* from official sources; writing asks *how to express it* in the user's compact style. Never use a giant prompt that treats a whole textbook and notebook as one context. Split by lecture/topic and fetch minimal anchored excerpts, with quality flags and a bounded token budget. Deduplicate repetitions between lecture and tutorial while retaining unique examples and important distinctions. Never hallucinate missing transcript content to fill a gold gap.

Derive a **versioned, editable style specification**, not a fine-tuned model or a single pasted exemplar. Inspect OOXML/LaTeX/notebook structures and sample prose for: heading depths/labels, lecture vs tutorial sequencing, bold/italics, bullets, notation, definition syntax, examples, diagrams, code execution, answer placement, TOC and sentence length. Have the user correct it. In the R Markdown notes the author explicitly says repeated concepts from tutorials were eliminated; preserve that intent without suppressing new tutorial insights. Across longer Word notes the author includes readings, lectures and tutorials with a TOC, many lists and hundreds of embedded figures; "brief tone" is not a request for a brief synopsis.

## 4. Add a renderer for each user-chosen module class

- **Word/DOCX (pilot):** treat the user's Word documents as style references; create a blank reference DOCX/style map without their content. Render headings, nested bullets, emphasized definitions, tables, figures/captions, equations, and TOC from the note model. Prefer a document pipeline capable of Word math (for example Pandoc plus a reference DOCX) rather than relying on plain text inserted by `python-docx`; use `python-docx` for structural checks and limited style control. Check opened/rendered pages, image placement, equation fidelity and page breaks. Do not infer styles solely from extracted text.
- **Python/IPYNB (second format):** Jupyter notebook with lecture/tutorial headings, concise markdown, executable code cells adjacent to explanations, examples and visible outputs. Preserve links/TOC if wanted. Use `nbformat` validation and isolated `nbclient` execution on intentionally runnable cells. Mark intentionally erroneous teaching examples as `expected_error` or non-executable; never run the entire user gold notebook or execute untrusted downloaded code on the host.
- **R Markdown (second coding variant):** keep YAML TOC and PDF/HTML choices, lecture/tutorial headings, dense bullets and labeled R chunks. Knit only in a sandboxed R environment with explicit package/data dependencies and expected outputs. Convert local `setwd()` paths into module-relative data references rather than copying machine-specific paths; the existing Rmd notes themselves warn about these. Validate chunk execution separately from output formatting.
- **LaTeX (third format):** preserve the mathematical note pattern: lecture sections, slide/topic subsections, interleaved tutorial exercises, compact itemized statements and explicit derivations/proofs with notation. Validate syntax/compile when TeX tools are available, review mathematical symbols and figures visually, and have a human check proof logic. Static compilation alone does not establish mathematical correctness.

Formatting should be classified by the user per module; subject-name heuristics are suggestions, not an override. All formats share the same evidence ledger, coverage plan and evaluation record. Never auto-apply a change to the user's existing notes; generated artifacts are new draft versions with a diff/review view.

## 5. Pilot acceptance, then broaden

1. Run only the Accounting development slice. Produce an extraction-quality report, source-coverage ledger, baseline and style-aware drafts; review mismatches against official pages and the disclosed gold. Fix the *cause* (missing source, bad extraction, selection, style or rendering), not the score.
2. Freeze code/prompts and test on the held-out Lecture 1/Tutorial 1 slice. Produce the five-axis scorecard, blind style comparison, and a failure list. If the core gate fails, stop and repair on a fresh development slice; do not retune on the locked test.
3. Challenge with numerical/figure-heavy Accounting material, then run a full-module draft only after the user approves the pilot. Verify coverage against all ten lectures/tutorials and report incomplete sources. Quizzes and mocks remain out of scope until notes meet the agreed gate.
4. Add DSA IPYNB using lecture-only/practice examples with homework restrictions; test code/output and missing online-preparation/tutorial materials. Add Introduction to Data Science Rmd using paired Rmd source/solution/data files and the user's Rmd notes. Add Mathematical Foundations TEX with math/handwriting/OCR/proof checks. Then broaden the Word format to Macro/Micro and others. Each new class gets a fresh development/held-out split and the same evidence/style/effectiveness measures, not a claim that Accounting scores transfer.
